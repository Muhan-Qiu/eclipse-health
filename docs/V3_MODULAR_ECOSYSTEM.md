## 1. 核心原则

1. **核心只做“容器 + 契约 + 数据”**：记录、权限、模块管理、基础 UI 外壳。
2. **功能即模块**：官方与第三方使用同一套接口，不搞特权内建。
3. **用户可替换**：设备适配、分析模型、仪表盘组件、报告模板都能换。
4. **默认可离线**：模块可本地安装，注册表可镜像；不强制联网。
5. **权限可见**：模块能读什么、写什么、是否联网，安装时明确展示。
6. **开放接口**：本地 REST/OpenAPI + MCP，既能被 AI 调用，也能导出数据给其他应用。
7. **优雅不被模块破坏**：UI 模块使用受控的设计令牌与声明式布局，不开放任意 CSS。

## 2. 模块类型

| 类型 | 作用 | 例子 |
|---|---|---|
| `device-adapter` | 解析设备/医院导出格式 | Apple Health、华为、Samsung、SCP-ECG |
| `signal-engine` | 预处理、质量检查、R 峰、特征提取 | 中值滤波、Pan-Tompkins、HRV |
| `analysis-model` | 逐搏/节律/未来健康模型 | Cardia 2.0、第三方 ONNX 模型 |
| `health-domain` | 新健康领域（记录类型+分析+页面） | EEG、PPG、睡眠、步态 |
| `dashboard-widget` | 首页卡片/图表 | 心率卡、HRV 趋势、波形缩略 |
| `exporter` | 报告/数据导出 | PDF、PNG、CSV、FHIR |
| `ai-tool` | 暴露给 LLM/Agent 的工具 | 查询记录、运行分析、导出报告 |
| `theme` / `locale` | 主题、字体、语言包 | 暗色变体、英文/中文 |
| `data-source`（未来） | 实时数据流 | BLE、串口、WebSocket |

## 4. 运行时与隔离（待决策）

推荐：**混合模式**

- 核心：Tauri 外壳 + React UI。
- Python 服务：核心 API + 模块宿主。
- 每个模块跑在**独立 Python 工作进程**（独立 venv，uv 管理），通过 JSON-RPC 与核心通信。
- 模块不直接访问数据库/文件/网络，全部经核心代理并记录审计。
- UI 模块优先用**声明式 JSON**（核心渲染），需要自定义交互时跑在**沙箱 iframe**，通过 postMessage 通信。
- 模型只允许 ONNX / safetensors；禁止加载不可信 pickle（PyTorch 权重可能执行任意代码）。

备选：

| 方案 | 优点 | 缺点 |
|---|---|---|
| 同进程 wheel 插件 | 最简单、性能好 | 无隔离，一个模块可崩溃/窃取全部数据 |
| 独立 Python 进程（推荐） | 隔离、可独立依赖、崩溃可恢复 | 通信与打包复杂度中等 |
| WASM 沙箱 | 最安全、可移植 | Python/ML 生态难落地 |
| Rust/Tauri 原生插件 | 性能最好 | 开发者门槛过高，违背开放目标 |

## 5. 分发模式（待决策）

推荐：**官方索引 + 社区索引 + 自定义源 + 本地安装**

- **官方索引**：签名 JSON，托管在 GitHub Pages；人工审核 + 自动扫描。
- **社区索引**：同一 schema，社区维护；默认可见但标注“社区”。
- **自定义源**：用户填索引 URL（类似 Obsidian/HACS）。
- **本地安装**：`.ehmod` 压缩包（manifest + 校验和 + 签名），适合离线/内网。
- 模块更新：稳定/测试通道；支持单模块固定版本、回滚。
- 注册表不托管大模型权重，只放 manifest + 下载地址 + 校验和；可配置镜像。

## 6. 信任、权限与审计（待决策）

权限示例：`records:read`、`records:write`、`files:user-selected`、`network`、`llm`、`models:download`、`ui:custom`、`system:notify`。

- 安装时逐项授权；运行时可撤销。
- 官方模块签名；社区模块可未签名，需用户显式允许。
- 所有敏感操作写审计日志（谁读了哪条记录、是否联网、调用了哪个模型）。
- 模块只能拿到完成工作所需的最小数据切片。
- 官方索引要求：OSI 许可证、模型卡、SBOM、自动安全扫描、禁止诊断性宣称。

## 7. UI 模块化（待决策）

- 首页 = 可拖拽/缩放的网格，用户自选组件（类似 Home Assistant Lovelace）。
- 组件 manifest 声明：数据源、配置 schema、最小/最大尺寸、刷新频率。
- 官方组件：心率、HRV、波形缩略、趋势、最近记录、快捷操作。
- 第三方组件：优先声明式；自定义 JS 只能跑 iframe 沙箱。
- 模块可贡献：侧边栏页面、设置项、命令面板项、报告模板、语言包。
- 设计令牌由核心锁定，模块只能使用主题变量，保证整体典雅。

## 8. 模型插件

- 模型 manifest：输入（导联/采样率/窗口）、预处理契约、输出类别、置信度、权重地址/校验和、运行时（ONNX/safetensors/远程 API）、硬件要求、基准结果、许可证。
- 强制模型卡：训练数据、指标、适用范围、局限、非诊断声明。
- 模型管理：下载、校验、安装、按任务选择、A/B 对比、回退。
- 安全：ONNX/safetensors；远程模型必须声明 `network` 权限；禁止不可信 pickle。
- 用户可同时安装官方 Cardia 与第三方模型，按记录选择。

## 9. AI / 外部应用接口（待决策）

- **本地 REST + OpenAPI 3.1**：绑定 `127.0.0.1`，Bearer token，按应用授权 scope。
- **MCP Server**：把记录、分析、导出、模块管理暴露为工具，供 Claude/ChatGPT 等调用。
- **事件流**：SSE/WebSocket 推送 `record.created`、`analysis.completed`。
- **数据导出**：JSON/CSV；FHIR 作为后续模块。
- 外部应用首次连接需用户确认；所有调用进审计日志。
- 反向：LLM 供应商配置本身也可做成模块（API Key / Ollama / 第三方网关）。

## 10. 数据契约与版本

- 核心表：`members`、`records`、`analyses`、`measurements`、`reports`、`modules`、`audit_log`。
- 模块数据：`module_id` + `record_type` + `payload_json`，模块不得直接读库。
- 核心 API 语义化版本；模块声明 `engines.eclipse: "1.x"`。
- 弃用策略：至少保留 2 个 minor 版本的兼容层。
- 模块卸载：用户选择保留或删除其数据；导出包含模块 ID 与版本。

## 13. 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 恶意模块窃取健康数据 | 模块能执行代码 | 权限、隔离、审计、签名、最小数据 |
| 依赖冲突 | 不同模块依赖不同版本 | 独立 venv / 锁文件 |
| UI 碎片化 | 第三方组件破坏美感 | 设计令牌、声明式 UI、审核规范 |
| API 频繁变动 | 社区模块失效 | 严格 semver、兼容层、弃用周期 |
| 医疗合规 | 第三方模型做诊断宣称 | 模型卡、免责声明、审核与下架 |
| 审核负担 | 模块数量增长 | 自动扫描 + 社区索引分级 |
| 可持续性 | 开源项目维护 | 赞助、基金会、商业支持 |

## 14. 建议的开发顺序

1. **Phase 0**：核心外壳 + 模块清单/权限/安装/审计 + 1 个示例模块（Samsung）。
2. **Phase 1**：Cardia 作为第一个 `analysis-model` 模块；心电分析主流程。
3. **Phase 2**：记录库、趋势、报告；官方 UI 组件。
4. **Phase 3**：Apple/华为/SCP-ECG 模块；模型管理器；社区索引。
5. **Phase 4**：AI API/MCP；插件开发工具与文档；社区治理。

> 关键判断：模块系统必须在写业务功能之前定下来，否则后期改造代价极大。
